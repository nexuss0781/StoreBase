# StoreBase runtime and Android reference

## Runtime topology

- `gateway/server.js` is a small Node HTTP server. `npm start` runs it; it reads `PORT` (default `8080`), validates the port, and binds `0.0.0.0`. It serves static files from `www/`, `GET /api/v1/health`, and the bootstrap endpoints. Build first (`npm run build`) so `www/index.html` and `www/telegram-direct.js` are current.
- Bootstrap returns encrypted Telegram settings only. The gateway does **not** proxy catalog messages, APKs, delta patches, icons, or update bytes. The app reads/downloads them from Telegram after bootstrap (gateway/README.md; gateway/server.js; src/telegram-direct.js).
- `app.yaml` identifies a Wasmer `App.v0` (`owner: tadi0781`, `name: storebase`, `package: .`) and declares a PostgreSQL capability. It contains no gateway entrypoint, deploy recipe, or secret declarations. The repository documents `STOREBASE_GATEWAY_PUBLISH_TOKEN` as a Wasmer secret, but does not document a Wasmer CLI deploy command. Do not infer one or deploy as part of local checks. The source-backed local run is `npm run build` then `npm start`; no Wasmer deployment is required.

## Bootstrap endpoints and runtime configuration

| Purpose | Endpoint | Settings returned | Required environment names |
|---|---|---|---|
| Catalog / Android read-only | `POST /api/v1/catalog/bootstrap`; legacy alias `POST /api/v1/telegram/bootstrap` | `schemaVersion: 1`, `settingsVersion: 1`, Telegram API ID/hash, **personal-user** read session, channel | `STOREBASE_TELEGRAM_API_ID`, `STOREBASE_TELEGRAM_API_HASH`, `STOREBASE_TELEGRAM_READ_SESSION`, `STOREBASE_TELEGRAM_CHANNEL` |
| CLI publisher | `POST /api/v1/publisher/bootstrap` | Above plus stored bot MTProto session (`botSession`); **does not return bot token** | Above plus `STOREBASE_TELEGRAM_SESSION`, `STOREBASE_GATEWAY_PUBLISH_TOKEN` |

`STOREBASE_TELEGRAM_SESSION` must be an authorized bot session whose bot is a channel administrator permitted to post. The read session must be an authorized personal MTProto user session with channel read access: Telegram bots cannot read channel history. `STOREBASE_TELEGRAM_BOT_TOKEN` is used by the CLI Telegram client only for initial/re-authentication when no valid stored bot session is available; it is not a bootstrap response or replacement for the stored session required by publisher bootstrap. `STOREBASE_GATEWAY_URL` is an optional CLI override (default `https://storebase.wasmer.app`); the CLI requires HTTPS except loopback and rejects URL credentials, query and fragment. `PORT` is optional for the server.

The publisher token must be high-entropy, 32–256 characters in `[A-Za-z0-9_-]`, kept separately in the gateway runtime and CLI runtime. Never put it in Android or the npm package. A missing/malformed gateway token leaves publisher bootstrap closed; publisher settings also require the saved bot session. `gateway/README.md`, `gateway/server.js`, `cli/lib/telegram-client.js`, and `cli/lib/gateway-client.js` are the configuration sources.

## Request and response security

The JSON POST is signed over newline-separated `STOREBASE_GATEWAY_V1`, method, **exact endpoint path**, app ID `com.nexuss0781.storebase`, UUID-v4 request ID, millisecond timestamp and DER/SPKI public key; publisher signatures also bind the token. Requests must be within five minutes of server time. The gateway checks RSA keys of at least 2048 bits, retains replay IDs for five minutes in process memory, and rate-limits each key fingerprint to 30 requests/minute by default. Each response uses a random AES-256-GCM content key wrapped with RSA-OAEP-SHA256; the envelope binds app ID, request ID and issuance time as authenticated data. Gateway settings are lazy-loaded/cached in process memory until restart; restart after credential changes or to clear that cache. Errors are intentionally generic to clients.

**Personal-use boundary, not production credential distribution:** the Android Keystore install key proves possession of that installation key, not that the requester is the official StoreBase APK. A client able to bootstrap can extract the read session. Anyone who gets the shared publisher token can obtain the bot session and publish to the channel. Limit and rotate that token if exposed; do not represent the Android bootstrap as app attestation. Response encryption protects transit/recipient binding; it does not make client-delivered credentials unextractable (gateway/README.md; gateway/protocol.js; SecureCatalogPlugin.java).

## Direct Telegram catalog and downloads

On Android, `SecureCatalog.getTelegramSettings` first reads its local encrypted cache; if absent/unreadable it calls the native gateway bootstrap. `src/telegram-direct.js` converts the Telethon-compatible session in memory, initializes `@mtcute/web` with `MemoryStorage`, verifies the account is a user (not bot), then searches the configured channel for `STOREBASE_MANIFEST_V1` messages (up to 5,000). It validates manifest IDs, versions, timestamps, hashes and artifact metadata; latest releases are sorted by publish time/message ID. It exposes `window.storeBaseCatalog`, `window.storeBaseTelegram` (`refreshCatalog`, `getRelease`, `downloadArtifact`, `disconnect`) and `storebase:catalog-ready` / download-progress events. Artifacts are fetched by Telegram message ID, cross-checked against the `STOREBASE_ARTIFACT_V1` caption, streamed to native storage, then checked against expected size and SHA-256. This is direct client-to-Telegram traffic, not a gateway catalog API.

The Android bridge keeps the install identity RSA key and cache AES key in Android Keystore. Cached settings are AES-GCM encrypted under a separate key in `noBackupFilesDir`; invalid cache data is deleted and triggers a fresh bootstrap. Converted Telegram authorization is in memory (not IndexedDB/localStorage). Android uses its legacy alias endpoint `/api/v1/telegram/bootstrap`; the catalog endpoint is the current API path.

## Frontend: working behavior vs mock UI

`index.html` implements the two-tab **visual** Apps/Explore shell: tab selection, arrow-key tab navigation, URL hash/query selection and scrolling/layout work. The displayed promotion, app rankings/recommendations, ratings, category examples, game cards, notification badge/profile and install labels are hard-coded mock content. Search/voice, chips, category/game cards, overflow, notifications/profile and install buttons have no action handlers; do not claim real search, filtering, installation, Play Store integration, or personalized discovery. The real Telegram catalog is initialized separately in Android and exposed as a JS global/event, but this HTML does not render it into those mock lists. In a normal browser there is no Capacitor native bridge, so Telegram catalog and update initialization are Android-only (`index.html`; `src/telegram-direct.js`).

## Android update, approval, reopen, limits

The update manager checks at startup and when returning to foreground after six hours. It gets the newest `storebase` release through the direct Telegram client. It chooses a delta only when its `fromVersionCode` exactly matches the installed version and the delta is smaller than the APK; otherwise it downloads the full APK. A `minimumVersionCode` above the installed code makes the dialog required/non-dismissible; optional updates can be deferred. Delta reconstruction or full APK staging and hash/package/version checks happen before launching Android’s package installer. Delta artifacts are limited to 256 MiB and APK/output to 1 GiB in the native update plugin.

On Android 8+ without “Install unknown apps” permission for StoreBase, the app opens that Android settings screen. The user must allow StoreBase, return to the app, and tap **Continue installation**. Android’s installer then requires user approval; StoreBase does not install silently. The `MY_PACKAGE_REPLACED` receiver attempts to relaunch StoreBase after replacement, but Android may defer/block background activity launches. If so, tap **Open** in the installer or launch StoreBase normally. The app checks package ID and version metadata; Android’s installer remains responsible for package signing continuity. Automatic reopening is best effort, not guaranteed (`src/update-manager.js`; StoreBaseUpdatePlugin.java; RelaunchAfterUpdateReceiver.java; AndroidManifest.xml; updates/README.md).

Troubleshooting: bootstrap may fail for bad/missing Telegram settings, invalid user session/channel access, stale clock (>5 minutes), a replayed request (409), rate limit (429), or unavailable settings (503). Verify that the reader session is a personal authorized user and resolves the same broadcast channel; the bot session must be authorized/admin for publishing. On update failure check Telegram access, manifest/artifact hashes and matching delta base; Android still requires unknown-app permission and installer confirmation. The gateway does not update catalog/release data itself.

## Operate locally, then deploy from a local checkout

Follow this ordered operator flow; deployment is a separate authorized action, never part of publishing an APK or installing this skill.

1. From the repository root run `npm ci`, `npm test`, and `npm run build`. Supply the gateway environment variables listed above from a private secret manager. The server does not load `.env` itself; inject environment variables using the environment's secret mechanism rather than assuming a file is loaded by `npm start`.
2. Run `npm start` and check `http://127.0.0.1:8080/api/v1/health` (adjust `PORT` if set). This health check is liveness, not proof the Telegram sessions are valid. Do not expose a local unprotected reader bootstrap to an untrusted network.
3. In another terminal set `STOREBASE_GATEWAY_URL=http://127.0.0.1:8080` through the shell's normal environment mechanism. Run `storebase-telegram list` to exercise reader bootstrap and Telegram authorization. Do not call the publisher route or upload a test app without write approval.
4. Before Wasmer deployment, install/authenticate the official Wasmer CLI and inspect `wasmer deploy --help`. Verify `app.yaml` targets the intended owner/app and that the account has permission. Do not change `owner` merely to make a command succeed. Inspect any database capability for operational/cost implications: this gateway does not itself use PostgreSQL.
5. Resolve the runtime packaging prerequisite **before** deployment. `package: .` points to local packaging, but this checkout contains no `wasmer.toml` or explicit Wasmer gateway entrypoint. A working Node local server is not proof that the selected Wasmer package runs `gateway/server.js`. Retrieve/review the existing app's actual runtime build configuration or use a supported Node-capable Wasmer template; ensure the package executes the gateway and includes built `www/`. Do not silently deploy a static-only frontend, guess a WASI runtime, or claim this missing recipe is already validated.
6. Configure all gateway secrets in the app's Wasmer dashboard under **Settings → Environment Vars**, then use **Save and Redeploy** when authorized. Include API ID/hash, bot session, personal read session, channel and publisher token; do not put them into `app.yaml` `env`, source, web bundles, or command arguments. `wasmer app secrets list` lists names without values; do not run `secrets reveal`. If a CLI-only setup is specifically required, the official `wasmer app secrets create --from-file=<private-file>` interface is available; keep that file outside source/package staging, restrict permissions, never print it, and remove it after use. Confirm flags against installed help.
7. Once the runtime package and secrets are ready and deployment is authorized, run `wasmer deploy` from the reviewed checkout/config directory. This may publish a runtime package and change the live app. Review prompts, intended owner/app and version; record the returned live URL. Inspect `wasmer app info` to confirm identity/URLs.
8. Check `<live-url>/api/v1/health`, set a client runtime `STOREBASE_GATEWAY_URL` to that HTTPS URL, and run a read-only catalog query. Test publisher authorization using automated mocked tests or an explicitly approved real release; do not publish an unapproved APK as a probe. Change the Android gateway URL only in native configuration/source if intentionally moving endpoints; a CLI environment override does not rewrite an installed Android app.
9. After rotating gateway sessions or publisher token, restart/redeploy to invalidate cached settings and update authorized CLI runtime secrets. Existing Android encrypted settings caches may retain the old reader session; clearing Android app data/reinstalling also changes local app state, so obtain approval and explain consequences before doing so.

Use [official Wasmer CLI deployment guidance](https://docs.wasmer.io/edge/cli/), [app configuration](https://docs.wasmer.io/edge/configuration/), and [secret management](https://docs.wasmer.io/edge/learn/secrets/) for the platform commands above. These are operator instructions, not a claim that a Wasmer deployment was executed or that the missing runtime packaging was repaired by this release.
